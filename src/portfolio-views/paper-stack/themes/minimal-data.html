How it works

gitrove is a discovery tool for open-source developers and repositories, built around a personal daily digest. A user signs in with GitHub, and gitrove watches the developers they follow and the repositories they star. Once a day it sends one digest: repositories where several people in their network are converging, new releases from starred repositories, who their follows started following, and everything else.

A free Discover page ranks rising developers by language and across 13 topic streams, such as MCP, AI agents and PostgreSQL. Ranking is relative to each developer's own baseline: their last 7 days of activity are compared with a 28-day baseline, smoothed by a constant. Minimum event and active-day floors keep out short bursts and bots. A weekly Founder's Digest, one real day of the founder's own digest, is published free on the blog as a sample. Pro has a 14-day trial, with billing through Stripe.

The backend is one Go binary on PostgreSQL. It uses the standard library's net/http and pgx, with no web framework. Its subcommands include serve, ingest, migrate, collect and mail. ingest loads GH Archive hourly event files in a daily batch and is the only writer of the ranking tables, with bot filtering and pruning. collect refreshes each account's network mirror and follow diffs through the GitHub API, and mail renders and sends digests through listmonk. The frontend is server-rendered Qwik City in TypeScript, with plain per-route CSS for a dark monospace design. A pull-based deployer polls main every minute and rolls back automatically. The app runs under systemd behind a Cloudflare Tunnel, and each pull request gets its own preview environment.

How it works

Crosscheck is a Claude Code plugin for checking the code an AI assistant writes. It has 30 skills, 5 agents and an MCP server with 7 tools across two engines. With Dafny, a pure functional core is specified and verified, then compiled to Python or Go. With Lean 4, an executable model acts as an oracle for differential random testing of the real implementation. Skills such as /reason, /locate-fault and /trace-execution add structured, semi-formal code analysis.

The repository also holds CGV, a contract graph verifier. A Rust extractor, built on ruff's Python parser, reads Django models, dataclasses and pydantic models. It stores their declared field and function constraints in SQLite. A checker written and proved sound in Lean 4 then checks that data passed between calls meets those constraints. Its soundness theorem says exit code 0 means every discovered data path is consistent. CI regenerates a manifest of the protected theorem statements and replays the proofs through Lean's kernel with leanchecker.

The Dafny and Lean toolchains run in sandboxed Docker containers with no network access and fixed memory and time limits. The plugin installs from the nicholls marketplace:

claude plugin marketplace add nicholls-inc/claude-code-marketplace
claude plugin install crosscheck@nicholls

No guarantee rests on the judgment of an LLM. An LLM may draft code, specs and proofs, but only deterministic checks and human judgment count as evidence.

How it works

Trakt, Plex Discover and TMDB lists were not personal enough, so I built a recommender for one person: me. Every night at 04:00 it retrains and publishes two ranked lists of 20 films and 10 series. One tab covers titles already in my Plex library. The other covers titles I don't own yet. Each title gets one verdict: programme it, return it, or rate it liked, meh or didn't like if I have already seen it. Every verdict becomes a training label. On the "Get it" tab, Order print files a request in Seerr, with an 8-second undo window when JavaScript is on. The library list is also mirrored into a "Watch next" collection in Plex, which stays in sync as I triage.

My watch history is small, so population data carries most of the weight. ALS item factors come from MovieLens 32M. A bag-of-tokens model of TMDB metadata, with a ridge mapping into the ALS space, gives vectors to new films and series that have no ratings. My labels then train a logistic reranker on six features, blended with popularity. No LLM runs when the page is served. The UI is a "projection booth at night": each title is a reel of film with its poster in a sprocketed frame, actions are enamelled levers, and every triage action has a keyboard shortcut. It renders on the server and works without JavaScript.

An autoresearch service improves the ranking model while I sleep. From 01:00 to 05:00 a coding agent, Codex or Grok, runs up to 30 experiments of 300 seconds each. It keeps a change only if it improves where the films I actually started ranked in a held-out month. The agent runs in a bubblewrap sandbox with none of my keys, no git history and network access only to its model API and PyPI. It may edit only the model package. My 20 most recent film starts stay hidden from it. Only a deploy gate run from a copy the agent cannot touch scores that data, and it ships a new model only when the score beats the live one. Across the first ten nights, between the agent's changes and my own, the baseline score fell from 0.40 to 0.16, where 0 means every film I started was ranked first.

The agent proposes and a fixed gate decides. Nothing ships on the agent's own say-so.

How it works

opsdeck is a local-first dashboard that an engineer runs on their own machine against their own gh login. It gathers every pull request they are connected to and sorts them into four bays: review requested of me, review requested of my team, authored or pushed, and commented or reviewed. Anything waiting on the user, such as a review request, red CI or a merge conflict, comes first. It is keyboard-driven (j/k, h/l, Space to lift a PR). Sending selected PRs to Claude Code review skills is designed into the UI, but in the current build that dispatch is simulated.

Work and personal organisations live in separate spaces, each with its own SQLite database and bot list. opsdeck also finds PRs opened by the user's GitHub App bots and by local Claude Code sessions, so PRs a login-only query would miss still appear. The metrics view covers merged PRs per week, cycle time at p50 and p90, first-pass yield, revert rate, review response time and review-queue age. Every figure shows its sample size and flags thin samples. An optional production view links Datadog and Sentry deploys to the commits they ship, for deploy frequency, batch size and merge-to-production lead time.

It ships as a single Go binary with no runtime dependencies. opsdeck serve binds to loopback only, serves an embedded static UI and a JSON snapshot API, and runs its own scheduler with 60-second and 15-minute ticks. It uses a pure-Go SQLite driver, so no CGO is needed. The screenshots below use invented demo data.

How it works

GoHome is a dashboard for homelab servers that run on Docker. It reads containers from the Docker socket and recognises common apps, such as Plex, Jellyfin, Home Assistant, Pi-hole, Nextcloud and the *arr stack, by matching image names, ports and labels against configurable rules. No service has to be registered by hand.

Services are grouped into stacks by Compose project. Each card shows whether the service is running, degraded, stopped or starting, with a launch link and Restart, Stop, Start and Logs actions. A status strip shows the Docker socket state and a tally of nominal, degraded and stopped services. Status is never shown by colour alone: each state has its own glyph and text label. There is a keyboard filter (/, j/k, Esc) and a recent-activity feed. The design brief follows Dieter Rams's "less, but better".

The backend is a Go service split into handlers, repositories and services. It uses Bun ORM on PostgreSQL, with migrations run at startup. A scheduler runs discovery with retries, a listener follows Docker events, and HTTP, TCP and Docker health checks feed status and metrics. Pages are server-rendered Go templates. Live updates are pushed over WebSockets as Turbo Streams, so there is no SPA framework or JavaScript build step. Config comes from YAML plus environment variables.
